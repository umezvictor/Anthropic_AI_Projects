# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this repo is

A research tool for studying COVID-19's impact on the well-being of society and businesses. The deliverable is a styled HTML report synthesized from two sources: a live web article and a local PDF. There are two separate implementations of the same pattern in this repo:

- `coordinator_agent.py` — a standalone Python script built on the **Claude Agent SDK** (`claude_agent_sdk`). This is the reference implementation of a coordinator-delegates-to-subagents architecture and is the one to extend going forward.
- `covid19_impact_report.html` — an earlier, manually-orchestrated version of the same report (produced by ad hoc subagent delegation in a Claude Code chat session, not by `coordinator_agent.py`). Kept as a reference artifact; not regenerated by the script.

This is not a git repository (no version control is in use here).

## Commands

Install the SDK (not vendored, not in a requirements file — install manually):
```
python -m pip install claude-agent-sdk
```

Syntax-check the coordinator script:
```
python -m py_compile coordinator_agent.py
```

Run the coordinator end-to-end (requires credentials — see below):
```
$env:ANTHROPIC_API_KEY = "sk-ant-..."
python coordinator_agent.py --mode compare   # default; also: sequential, parallel
```

`--mode sequential` runs one subagent per `query()` call, awaited one after another. `--mode parallel` issues a single `query()` call whose prompt instructs the coordinator to emit both Agent tool calls in the same turn. `--mode compare` (default) runs both and writes `latency_report.json`; it costs roughly 3x the API calls of a single mode, so use `--mode parallel` alone for a normal run.

Exercise the error-propagation / partial-results path deterministically:
```
python coordinator_agent.py --mode sequential --simulate-timeout document-analysis
```
This forces that subagent's timeout to ~0.01s so it fails every time, while the other subagent runs normally — use this instead of waiting on a real network timeout. Only meaningful in `--mode sequential` (see the parallel-mode timeout caveat below); on `parallel` it takes down the whole shared batch instead of just the targeted subagent.

There is no test suite, linter, or build step in this repo.

### Credentials

`coordinator_agent.py` spawns its own Claude Code subprocess via the Agent SDK and makes real, billed API calls — this is entirely separate from whatever Claude Code session is editing this repo. It requires `ANTHROPIC_API_KEY` or `ANTHROPIC_AUTH_TOKEN` to be set in the shell that runs it and exits immediately with a clear error if neither is present. Environment variables do not persist across separate shell invocations in this environment (each PowerShell/Bash tool call is a fresh process) — set the key in the same command as the `python` invocation.

## Architecture: `coordinator_agent.py`

A coordinator process that delegates to two isolated subagents, then synthesizes their findings itself. Subagent delegation can run two ways; `main()` picks one or both based on `--mode`:

```
Coordinator (main())
  sequential: run_subagents_sequential(tasks)
    -> query() #1: "web-research" subagent       [tool: WebFetch]
    -> query() #2: "document-analysis" subagent  [tool: Read]
  parallel: run_subagents_parallel(tasks)
    -> ONE query() call; coordinator model emits both Agent tool_use
       blocks in the same turn; subagents execute concurrently
  each subagent's raw output -> parse_findings() -> structure_findings() (repair fallback)
  -> findings_web.md, findings_doc.md (always written, regardless of mode)
  -> synthesize()  (coordinator itself, no further delegation)
       -> covid19_coordinator_report.html  (per-claim attribution, coverage gaps)
       -> provenance.json       (incl. structured error context for failures)
       -> latency_report.json   (only meaningful timing in --mode compare)
       -> attribution_check.json (independent, non-LLM verification pass)
```

Key design points that are load-bearing, not incidental:

- **Subagents never inherit conversation context, in either mode.** A Claude Agent SDK subagent's context starts fresh on every call and only ever receives its own `AgentDefinition.prompt` plus whatever string is passed as the Agent tool's prompt. Both `run_subagent()` (sequential) and `run_subagents_parallel()` build a prompt that embeds the full task (URL or file path, plus exactly what to extract) per subagent — there is no other channel by which a subagent could learn what to do, and `SubagentTask` is the single source of truth both code paths read from so they stay in sync.
- **Parallel mode relies on the model, not `asyncio.gather`.** `run_subagents_parallel()` does not fan out two Python-level `query()` coroutines concurrently — it issues *one* `query()` call and instructs the coordinator model to emit every Agent tool call in the same assistant turn. The Messages API executes multiple `tool_use` blocks in one turn concurrently and returns all `tool_result`s together; that's the actual mechanism being exercised here. Per-subagent start/finish times are reconstructed by watching for `ToolUseBlock` (dispatch) and the matching `ToolResultBlock` (completion) by `tool_use_id`, not by timing Python coroutines.
- **Background-task trap:** when asked to run subagents "in parallel," the coordinator model may set `run_in_background: true` on the Agent calls, in which case the `tool_result` it gets back immediately is just an "Async agent launched" acknowledgment — not the subagent's real findings. The parallel prompt explicitly requires `run_in_background: false` on every call, and `_is_background_launch_ack()` is a safety net that marks a result as `status="error"` if a launch-ack slips through instead of silently treating it as real content. If you see suspiciously fast/empty parallel results, check this first.
- **Capturing the WRONG output is an easy mistake in the sequential path.** The top-level coordinator's own final chat message (its paraphrase of "the subagent found X") is NOT the same thing as the subagent's actual output, and the two can diverge arbitrarily once a subagent is involved. `run_subagent()` deliberately extracts the Agent tool's `ToolResultBlock` (arriving in a `UserMessage`) as the real subagent output, and keeps the coordinator's own `AssistantMessage`/`ResultMessage.result` text only as a last-resort `partial_output` fallback. If you ever see findings that read like a *summary of a summary*, check which of these you're reading from.
- **Structured findings, not free-form prose.** Each subagent is asked to end its response with a `STRUCTURED_FINDINGS_JSON:` marker followed by a JSON array of `{claim, evidence_excerpt, source, publication_date}` objects — separating claim content from source/date metadata so the synthesis step can cite per-claim. `parse_findings()` validates the shape strictly (rejects anything missing a required key) and is deliberately lenient about *where* to find the JSON (marker text, a code fence, or a bare `[...]` substring, in that order) because models are unreliable about the exact wrapper even when they do comply.
- **The structuring instruction alone is NOT reliable — budget for the repair pass.** Empirically, a research subagent asked to both use tools (WebFetch/Read) *and* end with strict JSON will often just ignore the JSON requirement and write a nice prose report instead, regardless of how the instruction is worded (system prompt, explicit marker, recency-reinforced reminder at the end of the task text — all three were tried and failed in testing). `structure_findings()` is the actual fix: a second, tool-free, delegation-free call whose only job is reformatting the subagent's raw prose into the required schema. Both `run_subagent()` and `run_subagents_parallel()` try `parse_findings()` on the raw output first (free, fast path if a subagent does comply) and fall back to `structure_findings()` only on failure. Don't remove this fallback thinking "the prompt should be enough" — it was not enough across every subagent/mode combination tested.
- **Tool scoping is the permission boundary.** Each `AgentDefinition` in `AGENT_DEFINITIONS` lists exactly one tool (`web-research` → `WebFetch` only, `document-analysis` → `Read` only). An unlisted tool is absent from that subagent's session entirely, not merely blocked.
- **Error propagation is structured, not a bare string, in both modes.** A failure — timeout, API error, transport error, malformed JSON, empty findings, or a background-launch ack — becomes an `ErrorContext` (`failure_type`, `attempted_query`, `partial_output`, `detail`) attached to a `SubagentResult(status="error")`, never a crash. `synthesize()` receives this full context per failed source and is required to render a "Coverage Gaps" section (not just "source unavailable") naming the failure type and attempted query. `main()` aborts only if *every* subagent fails; a single failure still produces a degraded-but-honest report built from partial results.
- **Timeouts are real, not simulated-only.** Every `SubagentTask` carries a `timeout_seconds` (default 180s) enforced via `asyncio.wait_for` around the subagent's `query()` consumption. `--simulate-timeout AGENT_KEY` forces one task's timeout to ~0.01s for deterministic testing. In `parallel` mode there is only ONE shared timeout for the whole batch (`min()` across tasks) — simulating a timeout there kills both subagents, not just the targeted one, because per-subagent cancellation isn't possible within a single shared `query()` call. Use `--mode sequential` to test one subagent's timeout in isolation.
- **Provenance is tracked independently of the model.** `write_provenance_manifest()` writes `provenance.json` directly from `SubagentResult` dataclasses in Python — it is not generated or summarized by the LLM, so it remains a trustworthy audit trail (agent name, source, tool used, status, findings/error, start/finish timestamps) even if the HTML synthesis step gets something wrong.
- **Attribution is verified, not just requested.** `synthesize()`'s prompt requires every claim in the HTML to be visibly tied to its source/date. `verify_attribution()` is a separate, non-LLM check afterward: it greps the generated HTML for each successful source's identity and a snippet of each claim's text, and writes the result to `attribution_check.json` — don't trust the model's own claim of compliance without this.
- **PDF reads must be batched to stay under the SDK's transport limit.** The Agent SDK's stdio control channel has a hard ~1MB message size limit; reading the whole `COVID19.pdf` in one `Read` call overflows it (`CLIJSONDecodeError: JSON message exceeded maximum buffer size`). The `document-analysis` agent's prompt mandates reading at most 3 pages per `Read` call (`pages="1-3"`, `"4-6"`, ...), and the task's `env` carries `CLAUDE_CODE_FILE_READ_MAX_OUTPUT_TOKENS=6000` as a belt-and-suspenders override (merged into the shared subprocess env in parallel mode). If you add new document sources, preserve this batching pattern or reads will silently fail with the same buffer error.
- **Side effect**: reading the PDF via the `Read` tool leaves a `COVID19_extracted.txt` cache file in the project root. This is produced by the SDK's own PDF-to-text handling, not by application code.

### Measured latency (one `--mode compare` run, 2026-10-14)

Sequential: 326.6s · Parallel (single coordinator response): 126.4s · **2.58x speedup**, 200s saved. These numbers include live network/API variance (web article fetch + an 11-page PDF read in 3-page batches) — re-run `--mode compare` for a fresh measurement rather than treating this as a fixed benchmark.

### Output files (regenerated on each run)

- `findings_web.md`, `findings_doc.md` — per-subagent output for debugging: either the structured findings JSON (success) or the full `ErrorContext` plus whatever partial output was captured (failure). Always reflect whichever mode's results `main()` used (parallel's, when `--mode compare`).
- `provenance.json` — machine-readable audit manifest: findings (success) or structured error context (failure) per source, with timestamps.
- `latency_report.json` — timing for whichever mode(s) ran; only has `speedup_x`/`seconds_saved` after `--mode compare`.
- `attribution_check.json` — independent check of whether the HTML actually preserved each successful source's identity and claim text; `all_successful_sources_attributed` is the headline field.
- `covid19_coordinator_report.html` — final styled report, written directly to disk by the synthesis step's `Write` tool call (not printed/returned through the script). Includes per-claim source/date attribution and a Coverage Gaps section for any failed source.
